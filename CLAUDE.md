# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Critical Rules

- **NEVER edit `flake.nix` directly** — It is auto-generated by flake-file. Edit source modules and run `nix run .#write-flake` to regenerate it.
- **MUST `git add` new `.nix` files before building** — import-tree uses git tracking; untracked files are silently ignored by `nix build` and `nix run .#write-flake`.
- **Never commit `sops.key` or `keys.txt`** — these contain private decryption keys.
- **Format before committing** — run `just fmt` to apply nixfmt-rfc-style.
- **`main` is PRs-only** — a GitHub ruleset rejects direct pushes. Branch (`<type>/<issue>-<slug>`), push, `gh pr create`, then `gh pr merge --squash` (squash-only; the branch is deleted on merge and the PR is the history). There are no required checks — CI can't fetch the private nix-secrets input — so `--auto` has nothing to wait for and GitHub refuses it.
- **For den/framework specifics, read the source** — den lives at `github:denful/den` (clone it; the `docs/src/content/docs/` guides + `templates/ci/` tests are the reference). The den docs site is den.denful.dev.

## Code Style

- **Formatter**: nixfmt-rfc-style (2-space indent, opening braces on same line)
- **Standard module header**: `{ inputs, den, pkgs, fleet, __findFile, ... }:` — include only what the module uses
- **Angle brackets are preferred** over dotted paths for aspect references in `includes` lists
- Use `lib.mkDefault` for values that hosts/users should be able to override; use `lib.mkForce` for invariants
- Aspect files define exactly one aspect; facet files aggregate aspects from the same category

## Architecture Overview

A modular NixOS / nix-darwin flake built on **den** (aspect composition),
**import-tree** (every `.nix` under `modules/`, `hosts/`, `users/` is imported —
`_`-prefixed paths are skipped) and **flake-file** (generates `flake.nix` from
`flake-file.inputs.*` declared in the modules that own them).

### Directory Structure

```
.flake/
├── flake.nix / flake.lock   # generated by flake-file / lock (commit both)
├── justfile                 # build / deploy / secrets commands
├── packages/<name>/         # local packages → pkgs.<name> (fleet-packages overlay)
├── modules/
│   ├── den/                 # den plumbing: namespace, defaults, schema, strict, settings, hm-backup, base-host
│   ├── flake/               # flake-parts only: dendritic, deploy-rs, deploy-targets, devShells, tests, sops helpers
│   ├── nix/                 # nixpkgs policy + overlays, fleet-packages, nix-index, nh, npins, wsl input
│   ├── config/              # cross-cutting: nix-settings, state-version, user-secrets, ssh-keys
│   ├── user/                # account aspects: password, shell, admin, groups, coop-player, restricted
│   ├── roles/               # whole-machine roles (t2-laptop)
│   ├── system/              # utils, ssh, disk (btrfs/zfs), fonts, printing, virtualization, samba-client
│   ├── networking/          # networkd vs NetworkManager, tailscale, network-10g
│   ├── hardware/            # facter, bluetooth, nvidia, cuda, zsa, apple-t2, disk-utils
│   ├── audio/               # pipewire, studio (musnix, raysession, rt-isolation), dante (inferno, statime, …)
│   ├── music/production/    # DAW/plugin side: host half + per-user `producer` half
│   ├── desktop/             # niri / gnome / kde, sddm, grub, mac keybindings
│   ├── apps/  coding/  gaming/  theme/
│   ├── cluster/             # k3s agent (joins the starcommand cluster)
│   ├── ci/                  # forgejo / github Actions runners
│   └── deployment/          # beacon ISO, nixos-anywhere helpers
├── hosts/<host>/            # <host>.nix (den.hosts entry + den.aspects.<host>), <concern>.nix, _data/, facter.json
└── users/<user>/            # <user>.nix (den.homes + den.aspects.<user>), modules/, dots/
```

Namespaces (`modules/den/namespace.nix`): **`fleet`** — every reusable feature
aspect, exported (starcommand consumes it); **`cody`** — Cody's private aspects
(`cody.ssh`, `cody.dots`, …). `den.aspects.*` is reserved for hosts, users and
host-qualified users (`den.aspects."cody@THEBATTLESHIP"`).

## Den Conventions (how this repo uses den)

Den source: `github:denful/den` — the guides under `docs/src/content/docs/`
(`explanation/where-config-lands.mdx`, `explanation/choosing-a-mechanism.mdx`,
`guides/aspect-settings.mdx`) and `templates/ci/` tests are authoritative.

### Aspects and references

```nix
# modules/gaming/steam.nix — a leaf
{ fleet.gaming._.steam = { description = "…"; nixos = { lib, ... }: { programs.steam.enable = true; }; }; }

# a facet only aggregates
fleet.gaming = { description = "…"; includes = [ <fleet.gaming/steam> <fleet.gaming/proton> ]; };
```

- Angle brackets need `__findFile` in the module args: `<fleet/gaming>` →
  `fleet.gaming`, `<fleet.gaming/steam>` / `<fleet/gaming/steam>` →
  `fleet.gaming._.steam`, `<den/define-user>` → `den.batteries.define-user`.
- `os = …` targets nixos + darwin at once; `user = …` targets
  `users.users.<name>` of the user in scope.
- Callable aspects use `__functor = _self: args: { name = "x(${…})"; … }` —
  give each instance a unique `name` when a host may include several
  (`fleet.ci._.forgejo-runner`). Prefer settings (below) for per-host knobs.
- Deprecated, never use: `den.lib.parametric`, `den.lib.take.*`,
  `den.lib.perHost/perUser/perHome`, `den._.mutual-provider`.
- Batteries are `den.batteries.*` (`den._` / `den.provides` are aliases). There
  is no `home-manager` battery any more — HM activates from
  `den.schema.user.classes = [ "homeManager" ]` (namespace.nix).

### Where config lands — the rule that matters most

| Written in | `nixos` / `os` | `homeManager` | `user` |
|---|---|---|---|
| host aspect or anything it includes | host OS | **dropped** | **dropped** |
| `provides.to-users` on an aspect the host includes | host OS | every user of the host | every user |
| user aspect or anything it includes | host OS **only via den bug #694 — don't** | that user | that user's account |
| `provides.to-hosts` on an aspect a user includes | every host the user lives on | — | — |
| `den.aspects."cody@THEBATTLESHIP"` | — | cody on THEBATTLESHIP only | — |

So:
- **Host-picked features** (gaming, desktop, hardware): system half in
  `nixos`, per-user half in `provides.to-users` (see `modules/gaming/gaming.nix`,
  `modules/desktop/environment/niri/niri.nix`).
- **User-picked features** (apps, coding, apple-fonts): per-user half in
  `homeManager`, OS bits in `provides.to-hosts.<class>` — never untargeted `nixos`.
- **Account settings** (password, shell, description) use the `user` class. It
  routes into nix-darwin too, so NixOS-only fields (`extraGroups`,
  `hashedPassword`) are gated on `host.class == "nixos"`
  (`modules/user/password.nix`, `modules/user/groups.nix`).
- **One user on one host**: `den.aspects."<user>@<host>"`
  (`hosts/THEBATTLESHIP/cody-studio.nix` — the studio PipeWire/Dante setup).

### Groups, admins, restricted accounts

```nix
(<fleet.user/groups> [ "video" ])          # every user the aspect reaches
(<fleet.user/admin-groups> [ "docker" ])   # only users with <fleet.user/admin>
```

Root-equivalent groups (docker, libvirtd, podman) always go through
`admin-groups`. Only cody includes `<den/primary-user>` / `<fleet.user/admin>`;
co-op accounts use `<fleet.user/coop-player>`. Restricted accounts (joshua)
include `<fleet.user/restricted>`, and host features wrap their per-user half:

```nix
provides.to-users.includes = [ (<fleet.user/unless-restricted> <fleet.gaming/player>) ];
```

(`excludes` can't do this — it only covers the excluder's own subtree.)

### Host facts are den.hosts data

```nix
den.hosts.x86_64-linux.THEBATTLESHIP = {
  timeZone = "America/Los_Angeles";              # schema option → time.timeZone
  deployment.ip = "100.68.255.30";               # → deploy-rs + .#deployTargets
  settings.cluster.k3s-agent.dedicatedTo = [ "minecraft" ];
  users.cody.extraGroups = [ "audio" "davfs2" "wireshark" ];
  users.joshua = { };
};
den.aspects.THEBATTLESHIP.includes = [ <fleet/hardware> <fleet.hardware/nvidia> … ];
```

Custom entity keys are declared in `modules/den/schema.nix` (strict mode,
`modules/den/strict.nix`, rejects undeclared keys on host/user/home). Deploy
targets are read from `den.hosts` by `modules/flake/deploy-targets.nix`
(`nix eval .#deployTargets`); there is no `fleet.deploy` aspect.

### Aspect settings — per-host knobs

`modules/den/settings.nix` + `_settings-type.nix`: an aspect declares typed
options under `settings`; the host sets them at the same path minus the `_`:

```nix
fleet.desktop = {
  settings.session = lib.mkOption { type = lib.types.enum [ "niri" "gnome" "kde" ]; default = "niri"; };
  nixos = { host, ... }: { services.displayManager.defaultSession = … host.settings.desktop.session …; };
};
den.hosts.x86_64-linux.igloo.settings.desktop.session = "gnome";
```

Existing settings: `desktop.session`, `grub.*`, `audio.pipewire.*`,
`audio.musnix.*`, `cluster.k3s-agent.*`. Declare `settings` on the static
attrset (not inside a function), once per aspect.

### Structural guards

"Include X only if the host has / lacks Y" is a `den.lib.policy.when` guard
reading `host.hasAspect` (safe in guards and class-module bodies, never in an
`includes` computation). Example, `modules/networking/networking.nix`:

```nix
(den.lib.policy.when ({ host ? null, ... }:
  host != null && !(host.hasAspect fleet.networking._.networkmanager))
  { includes = [ fleet.networking._.networkd ]; })
```

### Defaults (`modules/den/defaults.nix`)

- `den.default.includes` — walked in every scope (hosts, users, standalone
  homes): define-user, inputs'/self', state-version, `fleet.nix`,
  user-secrets, hm-cli, base-host, no-man-cache. Anything with a
  `homeManager` half that every home needs goes here.
- `den.schema.host.includes` — hosts only: nix-settings, hostname.
- `den.schema.hm-host.includes` — hosts embedding home-manager: hm-backup.

### Roles

Machines of one kind share a role aspect instead of copied host files:
`fleet.roles._.t2-laptop` (nomad, stowaway) derives disk labels from
`host.name`; the host files only carry data (`deployment.ip`, `timeZone`).

## Host Declaration

```nix
# hosts/nomad/nomad.nix
{ __findFile, ... }:
{
  den.hosts.x86_64-linux.nomad = {
    description = "MacBookPro15,1 (T2) — covert field unit, dual-booted with macOS";
    users.cody = { };
    timeZone = "America/Los_Angeles";
    deployment.ip = "192.168.0.139";
  };
  den.aspects.nomad.includes = [ <fleet.roles/t2-laptop> ];
}
```

The host aspect defaults to `den.aspects.<name>`; don't set `aspect =`.
WSL: `wsl.enable = true` on the entry (den's wsl battery, see
`hosts/outrider/outrider.nix`). Declaring only a subset of a host's users in
a variant deletes the others on switch.

## User / Home Declaration

```nix
# users/bri/bri.nix
{ __findFile, ... }:
{
  den.homes.x86_64-linux.bri.userName = "bri";   # standalone home
  den.aspects.bri = {
    includes = [
      <fleet.user/coop-player>
      (<fleet.user/password> { method = "hashed"; value = "$6$…"; })
    ];
    user.description = "Bri";
  };
}
```

A host gets the user via `den.hosts.<sys>.<host>.users.bri = { };`. Login
shell: `(<fleet.user/shell> "nushell")` (also handles nushell) or
`(<den/user-shell> "bash")`.

## Adding Flake Inputs

`flake.nix` is generated — never edit it directly. To add a new input:

1. Declare the input **inline in the feature module that owns it** (the
   dendritic idiom — see `modules/coding/cli/herdr.nix`); only core/shared
   inputs live in `modules/flake/dendritic.nix`:
   ```nix
   flake-file.inputs.<input-name>.url = lib.mkDefault "github:owner/repo/vX.Y.Z";
   flake-file.inputs.<input-name>.inputs.nixpkgs.follows = "nixpkgs"; # if applicable
   ```
   Pin a release tag, not a branch, when upstream tags releases.

2. Regenerate `flake.nix`:
   ```bash
   nix run .#write-flake
   ```

3. `git add flake.nix flake.lock <the module>` and commit.

4. Access the input in modules via the standard `inputs.<input-name>` argument.

## Custom Packages (fleet-packages overlay)

Every `packages/<name>/package.nix` is auto-discovered by
`modules/nix/fleet-packages.nix` into ONE overlay applied to nixos, darwin,
and homeManager — consumers just use `pkgs.<name>` (or
`pkgs.<name>.override { … }`); never write relative
`callPackage ../../packages/...` paths in aspects.

- Names colliding with nixpkgs attrs get a `fleet-` prefix (listed in the
  module's `collides`) so the overlay never shadows nixpkgs. If nixpkgs later
  gains an unprefixed local name, using it throws and points at `collides`.
- Packages needing args from flake inputs go in the module's `extraArgs`,
  guarded per-system with `lib.optionalAttrs (input ? ${system})`.
- Multi-package dirs (mactahoe, tiagolr) are wired explicitly with flattened
  names (`mactahoe-gtk-theme`, `tiagolr-time12`, …).
- The same attrset backs the flake's `packages.x86_64-linux.*` outputs.

Underscore-prefixed files/dirs (`_data/`, `_lib/`, `_nvf_modules/`) are
invisible to import-tree — use them for plain-Nix data and helper functions.
Host-specific config lives in `hosts/<host>/<concern>.nix` as
`den.aspects.<HOST>-<concern>` added to the host's includes (plain data in
`hosts/<host>/_data/`); do not grow a host file's inline nixos block.

For verifying pure refactors (drvPath / nix-diff workflow, the registry.json
cascade, and the list-reorder caveat) see `docs/refactor-verification.md`.
The `den-fleet` agent skill (`skills/den-fleet/SKILL.md`, installed to
`~/.claude/skills/` via home-manager) carries the same conventions.

## Secrets Management (SOPS + central nix-secrets repo)

All secrets live in the **private** repo `github.com/Codys-Wright/nix-secrets`
(local checkout: `~/nix-secrets`, override with `$NIX_SECRETS_DIR`), consumed as
the `nix-secrets` flake input
(`git+ssh://git@github.com/Codys-Wright/nix-secrets.git?ref=main&shallow=1`).

**GitHub is the source of truth** for both this repo and `nix-secrets` — in each
checkout `origin` is the GitHub remote, so a plain `git push` is correct. The old
Codeberg remotes survive, demoted, as `codeberg`; they are not kept in sync and
must not be treated as authoritative. Any machine running `nix` needs a
GitHub-authorized SSH key, since the input is fetched over SSH at eval time.

After committing in `~/nix-secrets`, `git push` **before** `just update-secrets`,
or hosts repin to a stale rev.

This `nix-fleet` repo is PUBLIC. **Never add PLAINTEXT secret material here.**
(Cluster manifests, nixidy and the argocd-sops encrypted Secrets live in
`~/.starcommand`, not here.)

- Hard secrets (sops): `${inputs.nix-secrets}/sops/hosts/<hostname>.yaml`,
  `…/sops/users/<username>.yaml`, `…/sops/shared.yaml`
- Soft secrets (plaintext vars — emails, LAN IPs, domains): flake outputs,
  e.g. `inputs.nix-secrets.networking.domains.selfhost`,
  `inputs.nix-secrets.networking.hosts.starcommand.vpnIp` — never hard-code
  `starcommand.live` / `10.10.10.1` in modules
- Always set `sops.validateSopsFiles = false` for input-based sops files
  (store paths can't be validated at eval time)
- Hosts decrypt with their SSH host key (`/etc/ssh/ssh_host_ed25519_key`
  via ssh-to-age); the host-level secret `keys/age` bootstraps the user age
  key into `~/.config/sops/age/keys.txt` for home-manager sops
- Edit: `just edit-secrets <name> [--host|--user]` (delegates to ~/nix-secrets)
- After editing: `just update-secrets` (repins the input — REQUIRED or hosts
  keep building with the old secrets)
- Key changes (.sops.yaml): `just rekey-secrets`; enroll hosts with
  `just add-host <name> <ip>` inside ~/nix-secrets
- **Never commit**: `sops.key`, `keys.txt`, or any unencrypted secret

In NixOS modules, access secrets via `config.sops.secrets."path/to/secret".path`.

## Common Pitfalls

1. **Forgetting `git add` before building** — import-tree only sees tracked
   files; an unstaged `.nix` file is silently invisible.
2. **Editing `flake.nix` directly** — regenerate with `nix run .#write-flake`.
3. **Missing `__findFile` in module args** — angle brackets fail with
   "undefined variable `__fleet`".
4. **`homeManager` on a host-included aspect** — dropped without warning; use
   `provides.to-users` (host-picked) or include it from the user (user-picked).
5. **Untargeted `nixos` on a user-included aspect** — works today only via den
   #694; use `provides.to-hosts` or the `user` class.
6. **`user` class on darwin** — routes into nix-darwin, which lacks
   `extraGroups` / `hashedPassword`; gate on `host.class == "nixos"`.
7. **`mkForce` in the `user` class** — den forwards an evaluated value, so
   priorities are lost; force via a real `nixos` definition
   (`users/joshua/account.nix`).
8. **Guards in scopes without a host** — `den.default` content is walked in
   standalone homes too; write `{ host ? null, ... }` in guards reached from there.
9. **Wrong context key** — `{ host, ... }` / `{ user, ... }` / `{ home, ... }`
   includes are silently skipped where the key is absent.
10. **`mkForce` vs `mkDefault`** — `mkDefault` for overridable defaults,
    `mkForce` only for invariants.
